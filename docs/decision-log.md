# 南枫批量改名决策记录

## D-001 产品名与平台发布名分离

- 决策：应用内统一显示“南枫批量改名”；仓库、Release 和资产显式包含 `Windows`。
- 原因：产品名保持简洁，同时避免未来 macOS 或其他平台产物混淆。
- 当前证据：`v1.1.0` Release、`南枫批量改名-Windows.spec` 与 Inno Setup 配置。
- 被替代：旧名称“南烛枫-批量改名”及其发布物。

## D-002 预览规则链是执行计划的唯一来源

- 决策：UI 只收集 `RuleSettings`；`apply_rules` 生成名称，`build_preview` 负责状态与冲突，`build_plans` 只提取可执行项。
- 原因：避免预览正确但真实执行使用另一套顺序或过滤条件。
- 约束：新增规则必须先进入 `RuleSettings` 与唯一规则链，再补预览和测试。

## D-003 先 BAT 验证，再按明确要求打包 EXE

- 决策：日常开发保留 BAT/PythonW 启动；达到可用状态且用户明确要求后才生成单文件 EXE。
- 原因：源码阶段错误可见、迭代快；冻结运行时单独验证，不能用构建成功替代启动成功。

## D-004 当前发布是便携版，不是安装器（已被 D-008 替代）

- 决策：`NanfengBatchRenamer-Windows-Portable-v1.0.0.zip` 明确标记 Portable，ZIP 内为单文件 EXE 和 README。
- 原因：项目没有安装程序、卸载项或系统级注册行为，不能误称 Setup。
- 替代说明：该判断只适用于 v1.0.0；v1.1.0 已增加真实安装与卸载行为。

## D-005 撤销采用单级 JSON 记录（已被 D-006 部分替代）

- 决策：仅保存最近一次成功批次，撤销后清空；不承诺多级历史或事务式回滚。
- 原因：在第一版范围内提供可解释、可检查的恢复路径，同时控制复杂度。
- 替代说明：单级历史仍保留，但逐项执行和部分成功语义已由 D-006 的整批事务替代。

## D-006 执行与撤销统一采用两阶段文件事务

- 决策：全部源文件先进入唯一临时名，再写入目标名；失败时使用第二组回滚临时名恢复整批原路径。
- 原因：直接逐项改名无法稳定处理仅大小写变化、名称互换和批次中途失败。
- 恢复：回滚失败必须生成 JSON 恢复清单；只有完整成功批次更新最近一次撤销记录。
- 验证：Windows 临时目录覆盖普通批次、仅大小写、名称互换、提交失败回滚和恢复清单。

## D-007 工作台使用基准像素等比缩放

- 决策：以 `2200×1152` 为基准，按当前屏幕 Qt 逻辑可用区域统一缩放字号和全部布局像素。
- 原因：用户要求低分辨率尽量保持原排版，不以折叠和重排作为主方案。
- 约束：文字与容器同步缩放并保持单行；跨显示器始终从基准重算，折叠只作为低于支持范围的备用路径。

## D-008 GitHub Windows 发布默认使用 Inno Setup 7 x64

- 决策：`v1.1.0` 起，GitHub 主资产使用带版本和平台名的 Inno Setup 安装程序，不再把裸 EXE 或 Portable ZIP 作为默认交付。
- 验证：安装包编译、隔离目录安装、载荷摘要、真实窗口启动、卸载目录和注册表清理均通过。
- 约束：上传并核对新资产后才能移除旧 Release；未签名和 SmartScreen 风险必须继续明示。
